# SRE Agent Memory Manager

A free, standalone, single-file web tool for browsing, editing, and deleting what PagerDuty's **SRE Agent** has learned about your services — without needing to write a single API call yourself.

## What is this?

PagerDuty's SRE Agent (available on the **PagerDuty Advance** add-on) builds up a knowledge base over time as it helps investigate incidents. That knowledge is exposed through PagerDuty's `sre_agent/memories` API, but there's no built-in graphical interface for browsing it, understanding what it means in plain English, editing it, or removing entries you no longer want the agent to use.

This tool is that missing interface. It runs entirely in your browser, talks directly to PagerDuty's REST API using your own API key, and never sends your data anywhere else.

## What it does

- **Browse memories by service** — see everything the SRE Agent has learned about each of your services, organized into four plain-English categories:
  | PagerDuty's term | Shown in this tool as | What it actually is |
  |---|---|---|
  | `service_profile` | **Service Knowledge** | Tech stack, infrastructure, dependencies the agent has learned about a service |
  | `incident_summary` | **Past Incident Memory** | A narrative summary of a specific past incident and how it was resolved |
  | `playbook` | **Playbook** | A confirmed root cause + step-by-step fix procedure |
  | `runbook` | **Runbook** | Lightweight reference info — log queries, label selectors, dashboard links |

- **Look up memories by incident ID** — instead of browsing by service, jump straight to everything associated with one specific incident.
- **Read memory content as rendered markdown** — PagerDuty stores memory content as markdown text; this tool renders it properly (headers, bold, lists, code blocks) instead of showing raw text.
- **Edit memory content** — correct outdated or inaccurate information directly, with changes written back to PagerDuty.
- **Delete memories** — permanently remove a memory from the agent's knowledge base, with a confirmation step showing exactly what you're about to delete, since this action cannot be undone.
- **Filter and search** — by memory type, or free-text search across content.
- **Hover tooltips everywhere** — every label and concept has an `i` icon explaining what it means, so the tool is usable by people who aren't familiar with PagerDuty's internal terminology.

## What it does *not* do

- It does not create brand-new memories from scratch — PagerDuty's API doesn't support that. Memories are generated by the SRE Agent itself as it handles incidents; this tool can only view, edit, and delete memories that already exist.
- It cannot restore a deleted memory. PagerDuty's API has no un-delete operation, and memories have no "redacted" state that keeps them visible — a deleted memory is simply gone from the agent's knowledge base.
- It does not manage incidents, on-call schedules, services, or anything else in PagerDuty — it is deliberately scoped to SRE Agent memory management only.
- It does not use any AI/LLM itself. There's no chat, no natural-language interpretation — it's a direct, deterministic interface over PagerDuty's REST API.

## Requirements

- A PagerDuty account with the **PagerDuty Advance** add-on enabled (the SRE Agent Memory API is part of that add-on; without it, the connect step will succeed but memory lookups will fail with a permissions error).
- A PagerDuty **User API Token** (not an account-level API key). Create one under **PagerDuty → My Profile → User Settings → Create API User Token**.
- Any modern desktop browser (Chrome, Firefox, Edge, Safari).

## How to use it

1. Download `pd-memory-manager.html` from this repository (or clone the repo).
2. Open the file directly in your browser — double-click it, or right-click → **Open With** → your browser of choice.
3. Paste in your PagerDuty User API Token and click **Connect**.
4. Select a service from the sidebar, or look up a specific incident ID, to start browsing its memories.

There is no installation, no build step, no server, and no dependencies to install. It's a single HTML file that runs entirely client-side.

## Privacy & security

- Your API token is **only ever sent from your browser directly to `api.pagerduty.com`** — there is no intermediary server of any kind.
- The token is held in memory for the duration of the browser tab and is **not** written to disk, cookies, or browser storage. Closing the tab clears it.
- No analytics, telemetry, or tracking of any kind is included in this tool.
- Because this is a static HTML file you're opening locally, you can (and should) inspect the full source yourself before trusting it with your API token — there's no minification or obfuscation hiding what it does.

## How it's built

This is a single self-contained HTML file with:
- [React 18](https://react.dev/) and ReactDOM, loaded from the unpkg CDN
- [marked.js](https://github.com/markedjs/marked) (bundled inline, not loaded from a CDN) for rendering memory content as markdown
- Everything else — UI, styling, PagerDuty API client logic — is plain JavaScript, pre-compiled from JSX and embedded directly in the file. There's no build step required to run it, since the JSX-to-JS compilation has already been done ahead of time.

If you want to modify the source, the original JSX (before compilation) is included in this repo as `app.jsx` for reference and future development.

## Known limitations

- **Results are capped at 100 memories per query, and there is no way to page past that.** Confirmed against the live API: `limit` is rejected above 100 (HTTP 400), the `offset` parameter is silently ignored, and the response contains no cursor, `more`, or `total` field. If a service has more than 100 memories, the rest are simply unreachable through the API. If you see exactly 100 results, assume there may be more.
- PagerDuty's published OpenAPI spec lists the playbook memory type as `incident_playbook`, but the live API actually returns `playbook`. This tool uses `playbook`, which is what works. If PagerDuty ever aligns the API to its own spec, playbook memories will start appearing under a generic fallback tab — that's the signal this needs updating.
- **The memories endpoint rate-limits aggressively** — noticeably tighter than PagerDuty's general REST limit, and tight enough that clicking through several services in quick succession can trip it. The tool handles this for you: it respects the `Retry-After` header, otherwise backs off (1s, 2s, 4s), retries up to three times, and shows a "Rate limited — retrying" notice while it waits. If all retries are exhausted it tells you to wait about a minute. Nothing is lost when this happens; just retry.

## API compatibility

The SRE Agent Memory API is now generally available and officially documented in [PagerDuty's REST API reference](https://developer.pagerduty.com/api-reference/) under **SRE Agent**. It exposes exactly three operations, all of which this tool is built against:

| Operation | Endpoint | OAuth scope |
|---|---|---|
| List memories | `GET /sre_agent/memories` | `incident.read` |
| Update a memory | `PUT /sre_agent/memories/{id}` | `sre_agent.write` |
| Delete a memory | `DELETE /sre_agent/memories/{id}` | `sre_agent.write` |

There is no endpoint to create a memory, to restore a deleted one, or to fetch a single memory by ID. Memories have no status field — deletion removes them outright.

> [!NOTE]
> Earlier versions of this tool called a `POST /sre_agent/memories/{id}/redact` endpoint, which does not exist in the published API; deleting therefore failed. If your copy shows a **Redact memory** button rather than **Delete memory**, it predates this fix — download the current `pd-memory-manager.html`.
